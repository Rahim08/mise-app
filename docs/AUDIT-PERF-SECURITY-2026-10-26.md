# Аудит скорости и безопасности — 2026-10-26

Жалоба: всё «долго думает» — загрузка инкассации, сохранение смены, склада, аванса.

## Скорость

### Главная причина — функции Vercel в США, база в Ирландии

Замер прода: `x-vercel-id: fra1::iad1::…` — запрос входит в Франкфурте, а функция
выполняется в **iad1 (Вашингтон)**. База Supabase — **eu-west-1 (Ирландия)**. Каждый запрос
функции к базе пересекает Атлантику (~80 мс туда-обратно).

Один вызов `/api/db` от сотрудника = 3–4 последовательных запроса к базе до основного
(проверка токена сотрудника → лимит запросов → подписка → [снимок «до» для журнала] → запрос).
Итого ~400–500 мс на вызов. Пустой запрос без авторизации отвечал 250–450 мс.
Сохранение смены на вебе = 7–8 вызовов подряд → 3–4 секунды.

Сама база быстрая: `inkassation_balance` считается за 0.5 мс, данных мало (168 смен).

**Исправлено:**
- `vercel.json`: `"regions": ["dub1"]` — функции в Дублине, рядом с базой. Каждый запрос к
  базе ~1–2 мс вместо ~80. **Вступит в силу после деплоя.**
- `/api/db`: лимит запросов и проверка подписки — параллельно (−1 round-trip на каждый вызов).
- Веб-сохранение смены (`app/manager/page.tsx`, `app/dashboard/(shell)/shifts/page.tsx`):
  смена / расходы / инкассация / прогулы пишутся параллельно, как в iOS.
- Склад веб (`StashApp.tsx`): обновление остатков и инвентаризация — позиции параллельно
  (было N последовательных запросов на N вкусов).
- Склад iOS (`StashView.swift`): удаление перемещения и инвентаризация — то же.

Ожидание после деплоя: сохранение смены ~0.3–0.6 с вместо 3–4 с; загрузка инкассации —
доли секунды.

## Безопасность

Проверено: изоляция ресторанов в `/api/db` (restaurant_id навязывается сервером на
select/insert/update/delete/rpc), запрет записи в staff/employees для не-владельца,
биллинг-колонки, cron (CRON_SECRET), Stripe webhook (подпись), PostgREST-встраивание.

| Важность | Где | Что было |
|---|---|---|
| ВЫСОКАЯ | `app/api/db/route.ts` upsert | Upsert без `onConflict` конфликтовал по `id` из запроса: сотрудник мог прислать id строки ЧУЖОГО ресторана и «перетянуть» её себе. Теперь upsert принимается только с `onConflict`, включающим `restaurant_id` (все легитимные вызовы так и шлют). |

## Склад — неудобства (аудит 2026-10-26)

Исправлено (веб + iOS):
- «Движения»: свёрнутая партия показывала только «N позиций» и время. Теперь — бренды
  (до двух + «+N») и причина (кроме автоматических «Поставка/Выдача в зал/Списание»).
- Ввод больше остатка при выдаче/списании подсвечивается красным сразу (раньше — только тост
  после «Сохранить», и только про первую ошибку).
- Бегущий итог граммов в ручном вводе (на iOS был только в «Из склада», на вебе не было).
- iOS: текст в полях бренд/вкус был `.white` — не виден в светлой теме.
- iOS: граммы, введённые в «Из склада» на «Приходе» для нулевых позиций, после переключения на
  «Выдачу» становились невидимыми, но считались в итог и уходили в сохранение.
- Веб: смена типа (приход/выдача/списание) в форме молча стирала все введённые строки.
- Веб: «Доступно» искалось с учётом регистра (iOS — без) — подсказка пропадала.
- Веб: «Изменить» было только у последней партии; теперь у любой раскрытой (как на iOS).

Не сделано (на обсуждение): на вебе нет группировки «бренд → вкусы» и режима «Из склада»
(есть на iOS); корректировки инвентаризации (тип inventory) не видны в ленте «Движения» —
только во вкладке «Инвентаризация».

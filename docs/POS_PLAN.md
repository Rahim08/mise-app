# MISE POS — Полный план системы
> Версия 1.0 · Дата: 2026-06-19 · Статус: Планирование

---

## Философия

**"Сделано как Apple. Работает как швейцарские часы. Живёт без интернета."**

Все существующие POS-системы делятся на два лагеря:
- Старые (iiko, R-Keeper) — мощные, но страшные. Windows-архитектура, UX из 2005-го.
- Новые (Poster, QuickResto) — красивые, но поверхностные. Инвентарь слабый, офлайн никакой.

Mise POS берёт лучшее из обоих: **глубину iiko + дизайн Apple**. 

Три принципа, которые нельзя нарушать:
1. **Ресторан торгует всегда** — нет интернета, сломался один iPad, нет ингредиентов на складе — касса работает.
2. **Без обучения** — новый официант вышел в первую смену и разобрался за 10 минут.
3. **Один источник правды** — данные одни, интерфейсы разные. Официант, повар, управляющий, владелец — все видят одно и то же в своём контексте.

```
└──────────────────────────────────────────────────┼─────┘
                                                   │
                                            Internet (если есть)

                                            │   (Облако)   │
                                            └─────────────┘
```

**Почему не iPad как мастер:**
iPad под iOS имеет ограничения на фоновые процессы и WebSocket-серверы. Mac Mini M2 (от €600) или Windows mini PC (Intel NUC, от €300) работает 24/7, потребляет 15-20Вт, запускает Node.js/Bun сервер без ограничений. Ставится под барной стойкой — тихий, маленький, незаметный.

**Рекомендация железа:**
- **Мастер:** Mac Mini M2 (8GB RAM, 256GB SSD) или Intel NUC i3
- **Касса/Менеджер:** iPad (любой, 2021+)
- **Официант:** iPhone (любой, iOS 17+)
- **KDS кухня:** iPad на стойке ИЛИ Samsung TV + Apple TV (AirPlay)
- **Принтер чеков:** Epson TM-T20III (LAN, €180)
- **Принтер кухни:** Epson TM-T20III (отдельный, на кухне)
- **Денежный ящик:** Любой с RJ11, подключается к принтеру
- **Терминал оплаты:** Stripe Terminal (Италия) / Местный банк (Азербайджан)

### 1.2 Сетевая архитектура — "Иммунитет к интернету"

#### Обнаружение мастера (mDNS / Bonjour)

Мастер-сервер регистрирует себя в локальной сети как `mise-pos.local` через mDNS (Bonjour). Все iOS-устройства используют `NWBrowser` (Network framework) для автоматического поиска — никакого ввода IP не нужно. Нашли сервер → подключились → работают.

```
Новый iPad в сети:
1. NWBrowser ищет _mise-pos._tcp в Bonjour
2. Находит mise-pos.local:8080
3. Устанавливает WebSocket соединение
4. Аутентифицируется PIN-кодом устройства
5. Получает начальный снэпшот данных
6. Работает в реальном времени
```

#### WebSocket протокол (LAN Real-time)

Все события — заказы, статусы столов, чеки, стоп-лист — летят через WebSocket:

```json
// Официант добавил блюдо
{
  "type": "order.item.added",
  "id": "uuid-v7",
  "table_id": "t-5",
  "item": { "menu_item_id": "m-42", "qty": 2, "modifiers": ["no-onion"] },
  "device_id": "iphone-waiter-1",
  "timestamp": "2026-06-19T19:45:00Z"
}

// Мастер рассылает всем подключённым устройствам
{
  "type": "order.updated",
  "table_id": "t-5",
  "order": { ... },
  "version": 147
}
```

Типы событий:
- `table.*` — статус стола (free/occupied/bill-requested)
- `order.*` — заказы (created/item.added/item.removed/sent-to-kitchen/closed)
- `kitchen.*` — KDS (item.started/item.ready/course.fired)
- `payment.*` — оплата (started/completed/refunded)
- `menu.*` — стоп-лист (item.stopped/item.available)
- `sync.*` — синхронизация с облаком

### 1.3 Data Lifecycle — Жизненный цикл данных

```
┌─────────────────────────────────────────────────────────────┐
│                    МАСТЕР-СЕРВЕР                             │
│                                                             │
│  ①  Событие пришло → сразу в SQLite (is_synced: false)     │
│                         ↓                                   │
│  ②  Рассылка через WebSocket всем устройствам              │
│                         ↓                                   │
│  ③  Если есть интернет → фоновая очередь в Supabase        │
│                         ↓                                   │
│  ④  Supabase подтвердил → is_synced: true                   │
│                         ↓                                   │
│  ⑤  При открытии новой смены:                              │
│      - Данные старше 48ч И is_synced=true → DELETE         │
│      - Данные старше 48ч И is_synced=false → ОСТАВИТЬ      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Защита от дублей (Idempotency):**

Каждое событие имеет UUID v7 (time-ordered). При повторной отправке в Supabase используется `INSERT ... ON CONFLICT (id) DO NOTHING`. Дублей быть не может — даже если мастер отправил одно событие трижды.

**Конфликты при переподключении:**

Если устройство потеряло связь с мастером и работало автономно (крайний случай), при переподключении используется стратегия `Last-Write-Wins` по timestamp для большинства данных. Исключение: **платежи** — они идут в очередь и обрабатываются последовательно, никогда не перезаписываются.

## Часть 2 — Приложения

### 2.1 iPhone — Waiter App

**Контекст:** Официант ходит по залу. Экран маленький, руки заняты, темно, шумно. Операции одной рукой.

**Главный экран:** Список столов (компактный). Цвет = статус. Тап → заказ стола.

**Экран заказа:**
- Поиск блюда (большая строка сверху)
- Категории — горизонтальный скролл чипов
- Сетка блюд — большие карточки (60pt минимум), фото, цена
- Заказ снизу — "drawer" который тянется вверх
- Свайп влево по позиции → удалить / изменить
- Кнопка "Отправить на кухню" — зелёная, во всю ширину

**Жесты:**
- Долгий тап по столу → контекстное меню (разделить счёт / перенести стол / позвать менеджера)
- Свайп по позиции влево → удалить (с подтверждением)
- Swipe вверх по drawer → полный заказ
- Pull-to-refresh → обновить данные

### 2.2 iPad — Cashier / Manager App

**Контекст:** Стоит на стойке. Основной терминал. Большой экран. Все операции.

**Split View:**
- Левая панель (40%): карта зала / список столов
- Правая панель (60%): текущий заказ / касса / меню

**Режимы (меняются по роли):**
- **Официант** → карта зала + заказы (как iPhone, но больше)
- **Кассир** → касса + история чеков + ящик
- **Менеджер** → все вышеперечисленное + скидки + компы + отчёты смены

### 2.3 iPad/TV — KDS (Kitchen Display System)

**Контекст:** На стойке в зоне раздачи или на TV. Повара смотрят не беря руки. Обновляется в реальном времени.

**Интерфейс:**
- Тёмный фон (не слепит)
- Крупный шрифт
- Карточки тикетов слева направо (новые слева)
- Цвет карточки по времени: серый → жёлтый (5мин) → красный (10мин)
- Тикет: номер стола / позиции / курс / комментарии
- Тап по позиции → готово (убирается из тикета)
- Тап по тикету → весь стол готов (курс готов к выносу)
- Фильтр по цеху: Всё / Горячее / Холодное / Бар / Десерты

**Уведомления официанту:**
- Когда повар закрыл тикет → официанту приходит push на iPhone: "Стол 5 — горячее готово"

### 2.4 Web — Back-Office (Admin)

**Контекст:** Управляющий на телефоне/ноутбуке. Это наш существующий Next.js dashboard — расширим его.

**Секции:**
- Аналитика (расширенная POS-версия)
- Меню (редактор с техкартами)
- Склад (приходные, расход, инвентаризация)
- Персонал (смены, зарплата)
- Настройки (принтеры, терминалы, фискал)
- AI-ассистент (чат)

## Часть 3 — Все модули (детально)

### 3.1 Карта зала

**Данные:**
```
Зал (floor)
  ├── Название (Зал / Терраса / Бар / VIP)
  ├── Фоновое изображение (план помещения)
  └── Столы[]
        ├── Номер / Название
        ├── Форма (round / square / rect)
        ├── Вместимость
        ├── Позиция X/Y (drag & drop в редакторе)
        └── Статус: free / occupied / bill-requested / reserved / blocked
```

**Редактор зала (back-office):**
- Drag & drop столов на план
- Изменение формы и размера
- Загрузка фото плана помещения как фон
- Создание нескольких залов

**На кассе/телефоне:**
- Визуальная карта с цветами статусов
- Бейдж с суммой на занятых столах
- Бейдж с временем ожидания
- Индикатор официанта ответственного за стол

### 3.2 Заказ — полный жизненный цикл

```
Посадка → Заказ открыт
  ↓
Добавление позиций (с модификаторами)
  ↓
Отправка на кухню (курсами или всё сразу)
  ↓
Кухня готовит → KDS
  ↓
Повар отметил готовность → Push официанту
  ↓
Официант вынес
  ↓
Гость просит счёт (кнопка на столе или официант)
  ↓
Пречек (pre-bill) — для гостя без оплаты
  ↓
Выбор метода оплаты
  ↓
Оплата → Фискальный чек
  ↓
Стол освобождён
```

**Операции с заказом:**
- Добавить позицию / удалить / изменить количество
- Модификаторы (до 3 уровней: группа → опции → суб-опции)
- Комментарий к позиции ("без глютена", "острое")
- Назначить курс (1-й / 2-й / Десерт / Напитки)
- Отправить курс на кухню (не весь заказ — только выбранные курсы)
- Перенести позицию → другой стол
- Объединить два стола
- Разделить чек:
  - По позициям (каждый платит своё)
  - По количеству гостей (поровну)
  - По сумме (гость вводит сколько платит)
- Скидка на позицию или весь чек
- Комп (за счёт заведения) — с обязательной причиной и авторизацией менеджера

### 3.3 KDS — Kitchen Display System

**Тикет = один стол при одной отправке на кухню.**

```
┌────────────────────────────┐
│ 🟡  Стол 7  ·  Иван        │
│ 00:04                      │
│ ─────────────────────────  │
│ ✓ Брускетта (без томата)  │
│ ○ Паста карбонара          │
│ ○ Ризотто с трюфелем       │
│ ─────────────────────────  │
│ 💬 Аллергия на орехи!      │
└────────────────────────────┘
```

**Управление:**
- Тап по позиции → отметить готовой
- Тап по заголовку → весь тикет готов
- Свайп тикета влево → убрать в историю
- Долгий тап → отменить (с уведомлением официанту)

**Цвета по времени:**
- 0-4 мин → серый (норма)
- 5-8 мин → жёлтый (внимание)
- 9+ мин → красный (срочно)

**Настройки KDS (в back-office):**
- Какой цех что видит (горячий / холодный / бар / десерты)
- Какой принтер кухни используется (можно и физическую бумагу)
- Звуковой сигнал при новом тикете

### 3.4 Касса и Оплата

**Виды оплаты:**
- Наличные (автоподсчёт сдачи)
- Карта (Stripe Terminal / местный эквайринг)
- Смешанная (часть нал + часть карта)
- Подарочный сертификат
- Безналичный перевод (для корпоративов)

**Скидки:**
- % от суммы
- Фиксированная сумма
- Промокод (из back-office)
- Happy hour (автоматически по расписанию)

**Компы:**
- За счёт заведения (весь чек или позиции)
- Обязательная причина (+ авторизация менеджера по PIN если роль = официант)
- Логируется в аналитике отдельно

**Чеки:**
- Пречек (распечатать для гостя до оплаты)
- Фискальный чек (после оплаты → принтер + Supabase)
- Email-чек (QR на чеке → ссылка)
- Возврат (с причиной, авторизация менеджера)

**Z-отчёт (закрытие смены):**
- Итог продаж за смену
- По методам оплаты
- Внесения / изъятия из кассы
- Скидки и компы
- Печатается автоматически при закрытии смены

**X-отчёт (промежуточный):**
- То же самое, но смена не закрывается
- В любой момент

**Открытие кассы:**
- Ввод начального остатка наличных
- Фиксируется время и сотрудник

**Закрытие кассы:**
- Пересчёт наличных (вводит кассир)
- Система показывает: ожидалось / посчитано / расхождение
- Инкассация (сколько забрали)
- Z-отчёт → печать → архив

### 3.5 Меню (расширенное)

**Структура:**
```
Категория (Закуски / Горячее / Напитки / Десерты...)
  └── Позиция
        ├── Название (все 8 языков)
        ├── Описание
        ├── Фото
        ├── Цена / Цены по прайс-листам
        ├── Граммовка (выход блюда)
        ├── Аллергены (EU-стандарт: 14 аллергенов)
        ├── Калорийность (ккал / Б / Ж / У)
        ├── Флаги: вегетарианское / веганское / острое / хит
        ├── Статус: активно / стоп / сезонное
        ├── Цех: горячий / холодный / бар / десерты (для KDS)
        └── Ссылка на техкарту → ингредиенты
```

**Модификаторы:**
```
Группа модификаторов (пример: "Степень прожарки")
  ├── Обязательная? (да/нет)
  ├── Мин. выбор / Макс. выбор
  └── Опции[]
        ├── Название
        ├── Доп. цена (может быть 0)
        └── Влияние на склад (опционально)
```

**Прайс-листы:**
- Основное меню
- Доставка (+15% или кастомные цены)
- Happy Hour (автоматически по расписанию)
- Банкет / Спецмероприятие

**Стоп-лист:**
- Официант или повар помечает блюдо как "стоп"
- Мгновенно исчезает из всех экранов и QR-меню
- Нельзя добавить в заказ
- Уведомление официантам: "Паста карбонара — СТОП"

### 3.6 Склад с Рецептурой — Полноценный

Это принципиальное отличие от нашего текущего Stash. Склад знает **что из чего сделано**.

**Ингредиенты:**
```
Ингредиент
  ├── Название
  ├── Единица: г / мл / шт / кг / л / упак
  ├── Категория: мясо / рыба / овощи / молочка / алкоголь / сухое / ...
  ├── Текущий остаток (теория)
  ├── Физический остаток (после инвентаризации)
  ├── Минимальный остаток → алерт
  ├── Цена закупки (последняя / средняя)
  └── Поставщик → ссылка
```

**Полуфабрикаты (Prep Items):**
Заготовки, которые готовятся заранее. Например: "Соус болоньезе" = говяжий фарш 300г + томаты 200г + лук 50г.
Полуфабрикат сам может быть ингредиентом другой техкарты (паста болоньезе = паста 120г + соус болоньезе 150г).

**Техкарта (Recipe):**
```
Техкарта "Паста карбонара" (1 порция)
  ├── Выход блюда: 280г
  ├── Время приготовления: 12 мин
  ├── Ингредиенты:
  │     ├── Паста спагетти:  120г  (потери 0%)
  │     ├── Гуанчале:         80г  (потери 5% = 84г закупки)
  │     ├── Яйцо:              2шт
  │     ├── Пармезан:         30г  (потери 3%)
  │     └── Перец чёрный:      2г
  └── Себестоимость: €2.40 (авто по ценам закупки)
```

**Потери при обработке:**
- Потери при чистке (брутто → нетто)
- Потери при термообработке
- Система считает сколько нужно купить сырья, зная выход

**Автосписание при продаже:**
При закрытии чека → система пересчитывает ингредиенты по техкартам → уменьшает теоретический остаток.
Если ингредиента меньше нуля → **виртуальный минус, касса НЕ блокируется** → алерт в бэк-офисе.

**Неблокирующий склад (ключевой принцип):**
```
Паста карбонара пробита в чеке.
Спагетти на складе: 50г (нужно 120г).
→ Продажа проходит.
→ Списание: текущий остаток = 50 - 120 = -70г
→ В бэк-офисе алерт: "⚠️ Спагетти: -70г. Проверь приход."
→ Менеджер добавляет накладную → остаток исправляется.
Ресторан торговал. Данные честные. Все счастливы.
```

**Движения склада:**
- Приходная накладная (от поставщика, с ценами)
- Выдача в зал / производство
- Акт списания (порча / проба / персонал / мероприятие)
- Перемещение между складами (если несколько)
- Инвентаризация (факт vs теория → автоматическая разница)

**Поставщики:**
- База поставщиков (контакты, условия)
- История поставок по каждому
- Ожидаемые поставки

**Заказ поставщику:**
- Система видит: остаток ниже минимума → предлагает создать заказ
- Менеджер подтверждает → PDF / email поставщику

### 3.7 Персонал

**Роли и доступы:**

### 3.8 Аналитика + AI-Ассистент

**Стандартная аналитика:**

Период:
- Выручка (нал / карта / онлайн)
- Количество чеков и средний чек
- Covers (количество гостей)
- Revenue per cover

По меню:
- Топ продаж по штукам и выручке
- ABC-анализ (A=хорошо продаётся И маржинально / C=никто не берёт)
- Фудкост по блюдам (себестоимость / выручка = %)
- Маржа (чистая прибыль по каждой позиции)
- Стоп-листы (что чаще всего кончается)

По времени:
- Тепловая карта: час × день недели = выручка
- Загрузка зала (covers / вместимость × 100%)
- Средние чеки по часам (завтрак / обед / ужин)

По персоналу:
- Продажи каждого официанта
- Скорость обслуживания (посадка → первый заказ → чек)
- Скидки и компы (кто злоупотребляет)

Склад:
- Теоретический расход vs фактический → потери %
- Фудкост за период
- Оборачиваемость запасов
- Динамика цен поставщиков

**AI-Ассистент (Conversational BI):**

Управляющий пишет или говорит вопрос — система переводит в SQL и отвечает по-человечески.

```
Управляющий: "Какой фудкост был на прошлой неделе?"

AI:
SELECT 
  SUM(cost) / SUM(revenue) * 100 as food_cost_pct
FROM pos_order_items oi
JOIN pos_recipes r ON oi.menu_item_id = r.menu_item_id
WHERE created_at BETWEEN '2026-06-12' AND '2026-06-18'

Ответ: "Фудкост на прошлой неделе составил 28.4%. 
Это на 2.1% выше вашей нормы (26.3%). 
Основной вклад: телятина (+€340 vs план). 
Проверьте накладную от 14 июня."
```

Архитектура AI:
1. Вопрос → Claude API (Sonnet 4.6)
2. Системный промпт = схема БД + контекст ресторана
3. Claude генерирует SQL
4. Система выполняет SQL
5. Результат → Claude → человеческий ответ

Голосовой ввод:
- iOS: `SFSpeechRecognizer` (нативный, работает офлайн)
- Web: `Web Speech API`

Примеры вопросов:
- "Какое блюдо самое прибыльное в этом месяце?"
- "У кого из официантов самые высокие продажи?"
- "Сколько я заработал сегодня к этому часу?"
- "Покажи топ-5 блюд которые чаще всего идут в стоп"
- "Сравни эту субботу с прошлой"
- "Сколько спагетти нужно заказать на следующую неделю?"

## Часть 6 — UI/UX Принципы

### Философия: "Сделано Apple"

1. **Один тап** — любое действие максимум в 2 тапа от главного экрана
2. **Крупные цели** — минимум 60×60pt для любой интерактивной зоны (работает в перчатках, в темноте, в запаре)
3. **Жесты как в Telegram:**
   - Свайп влево → быстрое действие (удалить / изменить)
   - Долгий тап → контекстное меню
   - Pull-to-refresh → обновить
   - Drag → перенести позицию / перетащить стол
4. **Нет модальных диалогов** — всё через bottom sheets (как в нашем текущем iOS)
5. **Состояния всегда понятны** — пустой экран имеет иллюстрацию и подсказку, не просто пустоту
6. **Цвет = смысл** — зелёный: готово / свободно, жёлтый: ждёт, красный: срочно / ошибка, серый: неактивно
7. **Скорость** — любой экран открывается мгновенно (данные уже в локальном SQLite)

### Тёмная тема как основная
POS работает в ресторане. Часто полутёмная обстановка. Тёмная тема не слепит ни официанта, ни гостей рядом. Светлая доступна в настройках.

### Звуки
- Новый заказ на кухне → короткий "дин"
- Оплата прошла → приятный "тон"
- Ошибка → тактильная вибрация + красный
- Отключаются в настройках

### Анимации
- Стол меняет цвет — плавно, 0.3s
- Тикет в KDS появляется — slide from right
- Блюдо добавлено в заказ — pop (scale 1.05 → 1.0)
- Оплата успешна — checkmark animation (как Apple Pay)

## Часть 7 — Фискальная интеграция

### Азербайджан (MDIA e-qəbz)

**Механизм:**
1. Чек закрыт → POST в MDIA API с данными чека
2. MDIA возвращает: номер чека, QR-код, timestamp
3. QR печатается на чеке
4. Гость может отсканировать и проверить чек на сайте MDIA

**Что нужно:**
- Регистрация в MDIA (юрлицо в Азербайджане)
- API-ключ и токен заведения
- VÖEN (налоговый номер)

**Офлайн-режим:**
Если нет интернета → чек сохраняется локально → при появлении сети → пакетная отправка в MDIA (у них есть такая возможность для случаев сбоя связи).

### Италия (Registratore Telematico)

**Механизм:**
1. RT-принтер (Epson FP-90III или Custom RT) — физическое устройство
2. Подключён к интернету напрямую (или через мастер)
3. При каждом чеке: мастер → HTTP запрос к RT → RT сам отправляет XML в Agenzia delle Entrate → печатает сконтрино
4. DGFE (электронный журнал) хранится в самом RT

**Порядок номеров:**
RT-принтер гарантирует последовательность — это его задача. Мы просто шлём данные.

**Что нужно:**
- RT-принтер (€400-700)
- Регистрация в Agenzia delle Entrate (активация RT)
- Partita IVA (налоговый номер)

**Без RT (для тестирования):**
Можно работать в режиме "предчек" — печатаем красивые пречеки без фискализации. Законно только для тестирования, не для реальной торговли.

## Топ-12 приоритетных находок (по влиянию на реальные деньги/безопасность живого продукта)

### CRITICAL

**1. Web Analytics вообще не показывает «Долги» — iOS показывает.** (`block-C`, C1)
Коммит `92f6076` заявлял фичу и на web, и на iOS — реально доехало только до iOS. `countsInRollup` на web молча выкидывает неоплаченные `shift_expenses` из всех итогов расходов, без единого UI-сигнала, что деньги пропущены. Владелец на web видит «Расходы: €1200», хотя реально €1450, из них €250 — открытый долг, который потом всплывёт задним числом в другом периоде как необъяснимый скачок.

**2. Запись оплаты ЗП — две несвязанные DB-записи, обе платформы.** (`block-C`, C2)
`inkassations.update` (списание из кассы) и `salary_payments.insert` (факт оплаты) — раздельные `await`, без транзакции. Если вторая запись падает после успеха первой — касса уже списана, но «оплачено» нигде не отмечено. Менеджер видит «ещё должен» и платит второй раз реальными деньгами за уже списанный долг. Портит `cumulativeInkass` и «remaining» одновременно.

### HIGH

**3. Баланс кассы на экране «прыгает» вверх сразу после сохранения смены с погашением долга — обе платформы.** (`block-A`, #1)
Погашено €100 из долгов при закрытии смены с €50 нала — в БД сохранено верно, но локальный `calc()` на следующий рендер не учитывает только что погашенное (`settledTodayTotal` не бампается после очистки `selectedDebtIds`). Менеджер сразу после сохранения видит на €100 больше нала в кассе, чем есть на самом деле. Само-исправляется только на reload дня.

**4. «Карточная» оплата ЗП может дважды вычитаться из одного и того же остатка.** (`block-A`, #2)
`monthly_card_amounts` (бюджетная часть) и `salary_payments.method==='card'` (факт оплаты) — два разных понятия «карта», нигде не сверяются. Запись оплаты методом «card» второй раз вычитает уже исключённую сумму из `cash`, может пометить сотрудника «оплачен полностью», хотя реальный нал ещё должен.

**5. Manager и Analytics считают «начислено на сегодня» по двум разным формулам — расходятся на ~17 п.п. в один и тот же день.** (`block-C`, C3)
Manager: линейная рампа над окном `daysInMonth+payoutDay`. Analytics: цикл, привязанный к дню выплаты, с ресетом. Пример: 31 день, выплата 10-го, сегодня 15 авг — Manager показывает 36.6% начислено, Analytics — 19.4%. Один менеджер, один день, одни деньги — два экрана врут друг на друга.

**6. Уволенный/отвязанный сотрудник сохраняет полный API-доступ бессрочно.** (`block-F`, #1)
Токен на 10 лет, `resolveCaller` берёт `apps`-права из подписанного токена и никогда не перепроверяет `staff.is_active`/`device_id` на пути данных — только при входе по PIN и в списках UI. `is_active=false` в БД ничего не отзывает на сервере. Бывший сотрудник с телефоном сохраняет доступ к `manager`/`stash` (кассовые данные) неограниченно.

**7. Лимит попыток PIN общий на весь ресторан — пара опечаток блокирует всю смену на 15 минут.** (`block-F`, #2 / дублируется в `block-G`, #1 как обратная сторона той же проблемы)
Ключ лимитера — `ip:restaurantId`, без `deviceId` (хотя он уже собирается). Общий Wi-Fi ресторана = общий IP на всех. 2-3 человека ошиблись PIN в разгар смены — залочен весь ресторан на 15 мин, включая владельца. Обратная уязвимость (`block-G`): распределённая по многим IP атака по-прежнему может перебрать 4-значный PIN владельца — 10000 комбинаций, ничего не лимитирует суммарно по `restaurantId`.

**8. Dayparting (расписание доступности блюда) проверяется только на клиенте — обходится прямым вызовом API.** (`block-E`, #1)
`/api/menu/order` никогда не проверяет `menu_items.schedule`. Гость с id блюда (закешированным/подсмотренным) может заказать «только для завтрака» или алкоголь/кальян вне разрешённых часов в любое время суток — комплаенс-риск, не просто баг UI.

**9. Веб-Stash игнорирует настраиваемый список категорий «бесплатный кальян» — iOS его читает.** (`block-D`, H1)
Web захардкожен фиксированным списком, не читает `restaurant_settings.free_hookah_categories`. Владелец переименовал категорию в настройках — iOS-персонал видит новую, веб-персонал застрял на старой.

**10. Веб-Stash не видит iOS-only тип движения «списание с заведения» — venueLeft расходится между платформами навсегда до ручной коррекции.** (`block-D`, H2)
iOS может списать 500г прямо с площадки (без бренда/вкуса как маркер) — web этот тип движения не запрашивает вообще и не умеет создавать. После такого списания web показывает завышенный остаток бесконечно.

### MEDIUM (выборочно — самое важное)

**11. Admin-имперсонация даёт полный owner-доступ к любому ресторану без единой записи в аудит-лог.** (`block-E` #3 / `block-F` #6)
Если единственный `ADMIN_EMAIL`-аккаунт скомпрометирован — читать/менять кассу/ЗП/склад любого клиента до часа за сессию, и не останется следа, кто и когда.

**12. `/api/db` (самый нагруженный эндпоинт) отдаёт клиенту сырой текст ошибки Postgres.** (`block-G`, #2)
Не эксплуатируется напрямую (вызывающий уже авторизован и заскоуплен), но противоречит собственной заявленной цели файла «не палить внутренние детали» — имена таблиц/колонок/constraint'ов утекают в ответ.

## Что уже хорошо (проверено, не находка)
- OAuth-флоу банковской интеграции архитектурно верный: код обменивается на сессию только на сервере, токен никогда не уходит клиенту, `bank_connections`/`bank_transactions` доступны на запись только сервису.
- `/api/db`-шлюз принудительно скоупит каждый запрос по `restaurant_id` независимо от клиента — подозрение на межарендную утечку в Manager снято.
- Stripe webhook: верификация подписи по сырому телу, claim/release-паттерн идемпотентности, `verifyOwner` не доверяет client-supplied id.
- `staffToken.ts`: constant-time сравнение, `typ`-дискриминатор против admin/staff token confusion, реальные tamper/expiry-тесты.
- Б6 взвешенный скоринг аудитов, реструктуризация People в «чистый личный вид», свайп/статус в Bookings — перепроверены, регрессий нет.
- Схема БД (CSV-снимок) сверена с кодом — расхождений не найдено, критические правила из CLAUDE.md (opened_at, inkassations.total, employee_id) соблюдаются везде.

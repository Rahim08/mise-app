## Часть 1. Три симптома, о которых сообщил пользователь

### С1. «Редактирование поставки/выдачи не сохраняется»
### С2. «Выйдешь из приложения — даже сохранённая поставка удаляется и списывается неправильно»

**Это один и тот же баг.** Корень — `replaceMovementBatch`.

`StashView.swift:493`
```swift
func replaceMovementBatch(_ old: [Movement], rows: [MovRow], reason: String) async -> Bool {
    guard !saving else { return false }
    await revertAndDelete(old)          // ← старый батч УЖЕ УДАЛЁН из БД
    return await saveMovement(rows, reason: reason)   // ← а этот может вернуть false
}
```

`saveMovement` имеет **пять точек раннего выхода**, каждая — до записи чего-либо:

| Строка | Условие выхода |
|---|---|
| `341` | `guard !saving` |
| `346` | `filled.isEmpty` — нет заполненных строк |
| `365` | `stockOf()` не нашёл позицию на складе |
| `367` | граммов больше, чем остаток |
| `369` | списание без причины |

При любом из них старый батч **уже стёрт безвозвратно**, а новый не записан. Итог: поставка исчезла, остаток склада откачен назад.

**Почему выход по 367 (`> item.quantity_g`) срабатывает постоянно при редактировании выдачи:**
`stockOf()` читает локальный `m.stock`, а `revertAndDelete` его **не перезагружает** (нет `loadWarehouse()` внутри). То есть проверка идёт против остатка, который ещё *не* учитывает откат старой выдачи. Правишь выдачу 100 г → 150 г при остатке 100 г → «осталось только 100 г», выход, старая выдача уже удалена.

**Почему пользователь не видит ошибку:** тост рисуется в `StashBody` (`StashView.swift:626`), а лист `AddMovementSheet` его перекрывает. Ошибка уходит в никуда.

**Почему «пропадает только после выхода из приложения»:** ранний выход не вызывает `loadWarehouse()`, поэтому локальный массив `movements` всё ещё содержит старый батч — в списке всё выглядит нетронутым. Перезапуск приложения → чтение из БД → батча нет.

Тот же дефект на вебе, `app/tobacco/page.tsx:466-476`: удаление старого батча и откат остатка идут *после* валидации, но валидация тоже сравнивает с `stock`, не учитывающим откат.

### С3. «Двойной быстрый тап Сохранить дублирует поставку; удаление сносит обе»

Три независимых механизма.

**С3-a. Дыра в гварде при редактировании (iOS).**
`saveMovement:341` защищён корректно: `guard !saving` и `saving = true` (строка 370) выполняются без единого `await` между ними — атомарно на MainActor. Дубликата при создании нет.

Но `replaceMovementBatch:493` ставит гвард и **сразу уходит в `await revertAndDelete(old)`, не подняв `saving`**. За время этого await (2×N сетевых запросов) вторая задача проходит гвард. Результат:
- `revertAndDelete` выполняется **дважды** → остаток склада откатывается на двойную величину;
- дальше одна или обе задачи пишут новый батч — **с разными `batch_id`** (`saveMovement:371` генерит новый UUID).

То же в `replaceVenueWriteoff:500`.

**С3-b. `saveShift` вообще без гварда (iOS).**
`StashView.swift:196`
```swift
func saveShift() async {
    saving = true; defer { saving = false }
    try await DB.from("hookah_sales").delete().eq("date", dateStr).run()
    ...
    try await DB.from("hookah_sales").insert(rows).run()
```
`.disabled(m.saving)` не спасает: два тапа в одном кадре ставят два `Task` до перерисовки. Порядок `delete1 → delete2 → insert1 → insert2` даёт **удвоенные продажи за день**. Плюс delete-then-insert неатомарен: обрыв связи между ними стирает смену целиком.

`saveInventory:509` — тоже без гварда.

**С3-c. На вебе гварда нет нигде.**
`app/tobacco/page.tsx:452 saveMov`, `:218 save`, `:513 saveInv` — `setSaving(true)` не успевает попасть в рендер, `disabled={saving}` ещё `false`. Второй клик проходит.

Именно веб объясняет «удаление сносит обе»: в режиме правки веб **переиспользует batch_id** (`page.tsx:465` `const batchId = editBatch || crypto.randomUUID()`). Двойной клик → две пачки строк под **одним** `batch_id` → iOS группирует их в одну карточку (`movementBatches:270`), и `deleteMovementBatch` сносит обе разом.

## Часть 2. Остальные найденные дефекты

### HIGH

**H1. Read-modify-write по кешу — остаток склада затирается.**
`saveMovement:372` и `revertAndDelete:462` читают `DB.from("tobacco_stock").select()` **без `.fresh()`**. `DBQuery` кеширует SELECT на 5 минут (`DB.swift:39`). Переменная называется `fresh`, но свежей не является. Инвалидация после записи — fire-and-forget `Task {}` (`DB.swift:14`), гонка с последующим чтением. Итог: `ex.quantity_g + delta` считается от устаревшей базы → правка теряется, остаток «списывается неправильно». В People такой же паттерн правильно использует `.fresh()` (`PeopleModel.swift:816`).

**H2. Остаток склада может уйти в минус и позиция пропадает из UI.**
`saveMovement:395` пишет `ex.quantity_g + delta` без `max(0,)`. Проверка лимита идёт по локальному `stock`, а списание — по `fresh`; при гонке получаем отрицательный остаток. Дальше `inStock` фильтрует `> 0`, `outOfStockCount` — `== 0`. Отрицательная позиция **не попадает ни в один список** — товар исчезает со склада насовсем.

**H3. Инвентаризация на iOS не корректирует склад.**
`saveInventory:509` только вставляет запись в `tobacco_inventories`. Веб (`page.tsx:517-521`) после этого прогоняет `tobacco_stock.update({quantity_g: actual})`. На iOS пересчёт фиксируется, но остаток не меняется — расхождение сохраняется навсегда.

**H4. Смена дня при сетевом сбое пишет цифры в чужую дату.**
`loadShift:84` при ошибке делает `return`, не тронув `paid`/`free`. Но `shiftDay:223` уже сдвинул `currentDate`. На экране — вчерашние кальяны с сегодняшней датой. Тап «Сохранить смену» записывает их в новый `dateStr`.

**H5. Удаление категории бесплатных кальянов стирает историю.**
`saveShift:207` итерирует по `freeCats` из настроек. `loadShift:99` кладёт продажу в `free[id][r.flavor]` для **любой** категории из БД. Если владелец убрал категорию в дашборде — старые продажи по ней читаются, но при следующем сохранении не переписываются, а `delete().eq("date")` их уже снёс. Плюс `freeTotalOf:171` их не считает — статистика врёт ещё до сохранения.

**H6. `saveShift` не перезагружает смену.**
После записи `savedGrams`/`savedQtyByType` (`:109-110`) остаются старыми. `gramsUsed:187` считает `savedGrams + delta от savedQtyByType` → плитка «Табак» и `venueLeft` показывают завышенный расход до ручного refresh. Повторный тап «Сохранить» удваивает показанное.

### MEDIUM

**M1. Ошибки в листе не видны.** Тост рисуется в `StashBody:626`, под модальным листом. Все `flash()` из `saveMovement`/`saveVenueWriteoff`/`saveInventory` теряются.

**M2. Переключение «Из склада» при редактировании стирает батч.** `commit():1138` берёт `pickedRows()`, `picks` пуст → `filled.isEmpty` → выход, старый батч уже удалён (тот же корень, что С1).

**M3. Все `try?` в `revertAndDelete`.** `:474` (откат остатка) и `:477` (удаление строк) глотают ошибку по отдельности. Провал отката = двойной учёт; провал удаления = откат без удаления. Тихо, без тоста.

**M4. Откат ищет позицию по бренду/вкусу, не по id.** `revertAndDelete:468` — `norm(brand)==norm(brand) && norm(flavor)==norm(flavor)`. Если позицию переименовали, `continue` без сообщения: движение удаляется, остаток не откатывается.

**M5. `loadShift` тянет всю историю без лимита.** `:72` `hookah_sales` и `:75` `tobacco_movements type=out` — селекты без `.limit()` и без диапазона дат. Растёт линейно с возрастом заведения; при упоре в потолок строк PostgREST `venueBase` начнёт молча врать.

**M6. `venueBase` для прошлых дат бессмысленен.** `loadShift:105` считает `pastGrams` как «всё, что не за выбранную дату» — включая дни *после* неё. Навигация в прошлое даёт неверный «остаток в зале».

**M7. Правка не сохраняет `batch_id` (iOS).** `saveMovement:371` всегда новый UUID. После правки батч уезжает вверх ленты как новый, история идентичности рвётся. Веб при этом id переиспользует — две платформы расходятся.

**M8. KPI-цели пишутся из Stash, но политика разрешает только Analytics.** `app/api/db/route.ts:40` — `hookah_goals: { write: ['analytics'] }`. `saveGoal:160` / `deleteGoal:165` вызываются из Stash через `try?`. Сотрудник с доступом только к Stash получает 403, цель молча не сохраняется. Владелец не заметит — ему `caller.owner` открывает всё.

**M9. Правка меняет глобальный фильтр ленты.** `primeForEdit:1147` пишет в `m.movMode`. Открыл правку выдачи на вкладке «Приход» — после закрытия лента показывает «Выдачу». Плюс сегмент внутри листа тоже привязан к `$m.movMode`: смена типа посреди правки меняет то, куда запишется новый батч.

**M10. `movements` ограничены 200 записями.** `loadWarehouse:235`. Батч за пределами последних 200 недоступен для правки/удаления, хотя в `venueBase` он участвует (там лимита нет) — расхождение между лентой и цифрами.

**M11. Веб: множественный откат одной позиции теряется.** `page.tsx:468-473` в цикле по старым движениям берёт `item.quantity_g` из несвежего `stock`. Два движения по одному товару в батче → второй `update` перетирает первый, откатывается только одна дельта.

### LOW

**L1.** `revertAndDelete:474` клампит в `max(0, ...)` — удаление прихода при уже израсходованном остатке молча теряет граммы.
**L2.** Три `.sheet` на одном вью (`StashView.swift:642-644`) — рабочий, но хрупкий паттерн SwiftUI; при изменениях стоит развести.
**L3.** iOS вставляет движение без `flavor_id`, веб — с ним (`page.tsx:483`). Расхождение схемы между платформами.
**L4.** `AddInventorySheet:1308` показывает все позиции включая нулевые; веб (`page.tsx:504`) — только `quantity_g > 0`.

## Часть 5. Доп. правки той же сессии (2026-08-02, после части 4)

**Дата/время движения показывались неверно (не всегда).** Корень: `tobacco_movements.created_at` — колонка `timestamp without time zone` (Postgres `now()` в UTC-сессии, без указания зоны в строке). `parseISO()` (iOS, `Theme.swift`) и `new Date(iso)` (веб) при отсутствии смещения в строке трактовали её как ЛОКАЛЬНОЕ время устройства/браузера — движение, сохранённое в 14:00 UTC, показывалось как «14:00» вместо верных 16:00 в Цюрихе (UTC+2), а рядом с полуночью дата целиком уезжала на соседний день. Починено: iOS — явный `UTC` для naive-форматов в `parseISO`; веб — добавляем `Z` к строке без смещения перед `new Date()` (`toUtcDate()` в `page.tsx`). Общий хелпер — фикс автоматически применился ко всем экранам, использующим `parseISO`/аналог (People и т.д.), не только к Stash.

Отдельная причина того же симптома: при РЕДАКТИРОВАНИИ движения `replaceMovementBatch`/`replaceVenueWriteoff` удаляли старые строки и вставляли новые без `created_at` — дата/время «прыгали» на момент правки. Починено: старый `created_at` явно передаётся в новую запись (iOS и веб).

**Новый UI ручного ввода движения (по запросу).** Раньше каждая строка была независимой (бренд+вкус+граммы) — при поставке из N вкусов одного бренда бренд приходилось вводить N раз. Теперь: карточка на бренд (AutoField бренда — один раз), внутри — строки вкус+граммы, «+ вкус» добавляет строку под тем же брендом, «+ бренд» под списком открывает новую карточку. Реализовано только на iOS (`MovGroup`/`MovLine` в `StashView.swift`, флэттенится в `[MovRow]` перед сохранением — модель/API не менялись). Правка существующего батча и AI-префилл группируются по бренду автоматически. Веб не трогал — там иной UI-стек (React), можно сделать отдельно по запросу.

Заодно нашёл и починил (тем же диффом, 1 символ): `isDirty` в `AddMovementSheet` был инвертирован (`!picks.values.contains{...}`) — пустой пикер «Из склада» считался грязным, попытка закрыть нетронутый лист спрашивала подтверждение отмены без причины.

Build/tsc прогнаны после каждого шага — чисто.

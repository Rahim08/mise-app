# Booking: локальные исправления и перепроверка

Статус: локальная реализация; публикации, применения SQL к рабочей базе и реальных
уведомлений не было. Существующие изменения других модулей сохранены. Исправления
выполнены параллельно по серверу, web и iOS, затем проверены отдельно.

## Исправлено

- Сервер проверяет действующие права сотрудника и доступность Booking по тарифу.
  Автор устанавливается сервером; изменения чужих броней и профилей блокируются.
  Массовые фильтры проверяются целиком, фактическая запись ограничивается проверенными
  ID и повторной проверкой автора/заведения в SQL.
- Ввод даты, времени, количества гостей, статуса и профиля валидируется.
  Новая бронь имеет постоянный UUID черновика: повтор после потери ответа не создаёт дубль.
  Старые клиенты без UUID принимаются, но такой повтор не имеет новой гарантии дедупликации.
- Запоздавшие ответы больше не подменяют выбранные даты, диапазоны, месяц и профиль.
  Ошибки загрузки показываются с повтором; пустое состояние не заменяет ошибку.
  Неудачное сохранение оставляет форму и введённые данные.
  В iOS подтверждённая запись сразу появляется локально; ожидание push и последующего
  обновления больше не удерживает форму сохранения. Это проверено с заблокированными ответами.
- Профиль загружается перед редактированием; сбой чтения не превращает сохранённые
  фамилию, email и день рождения в пустые значения. Черновики привязаны к гостю.
  Точный запрос выбранного профиля устраняет зависимость от лимита массовой выборки заметок.
- Введён постоянный `guest_key`: одинаковые последние девять цифр и одинаковые имена
  больше не объединяют людей. Полный номер группируется только внутри одного заведения;
  изменение контактов сохраняет идентификатор. Гости без телефона не сливаются по имени.
  Конфликт телефонов проверяется при создании, обычном изменении брони и изменении гостя.
- Изменение гостя и удаление его броней/заметок выполняются атомарно. Неуказанные поля
  профиля сохраняются. История бронирований читается страницами без скрытого годового лимита.
- Будущие брони не считаются посещениями; отмены не меняют последнюю дату визита.
  Для совместимости старые неотменённые брони считаются визитами; за сегодня — только arrived.
  В iOS исправлены Tomorrow, обновление без пятиминутного кэша и гонки смены статуса.
- Google Reviews использует последние 90 снимков; ошибки настройки/синхронизации не скрываются.
  В web строки гостей доступны с клавиатуры; гостю без имени не подставляется подпись поля.
- Уведомление формируется только из сохранённой доступной брони, с ограничением частоты.
  Временная аренда с токеном разрешает повтор после сбоя до записи журнала. Детерминированный
  ID получателя предотвращает дубли журнала; push отправляется только новым строкам журнала.

## Сохранность данных и будущий выпуск

Миграция `docs/migrations/booking-guest-identity-2026-11-13.sql` добавляет поля, индексы
и служебные функции. Она не удаляет старые брони/заметки. Старые заметки копируются
только при однозначной связи; неоднозначные остаются в исходном виде для отдельного
разбора, без автоматического присвоения другому человеку при повторе миграции.
Новая явная операция удаления гостя удаляет только его группу и однозначно связанные заметки.

Перед будущим согласованным выпуском требуется применить эту миграцию, затем выпустить
сервер/web и обновлённое iOS-приложение. Старые клиенты с прежними ключами заметок требуют
обновления: запись по неоднозначным/устаревшим ключам блокируется. Автоматическое объединение
местных и международных форматов номера не выполняется.

Рабочая база, её RLS и реальные APNs/Google API в этой проверке не изменялись и не
проверялись сквозным сценарием. Push после записи журнала остаётся best effort; строго
однократная внешняя доставка и фоновая очередь повторов не заявляются. Перенос региона
и измерение скорости на реальной сети остаются частью отложенного выпуска, не этой проверки.

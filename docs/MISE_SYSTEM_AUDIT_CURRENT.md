## Previous Hypotheses — verification results

### AUTH-01 — Права доступа в токене живут дольше, чем сами права

**Статус:** CONFIRMED. **Severity:** Critical.

**Evidence:**
- `lib/staffToken.ts:14-22` — `issueStaffToken()` зашивает `apps: string[]` прямо в подписанный payload токена при логине по PIN. TTL = 10 лет.
- `lib/apiAuth.ts:36,45,52,58` — `resolveCaller()` возвращает `apps: staff.apps || []`, где `staff` — это **декодированный payload токена**, не свежая строка из БД.
- `lib/apiAuth.ts:19-26` — `staffTokenRevoked()` перепроверяет по БД только `is_active`, `apps` не сравнивается вообще.

**Текущее поведение:** владелец меняет `apps` сотруднику в `app/dashboard/(shell)/team/page.tsx` — запись в БД меняется немедленно, но уже авторизованное устройство продолжает использовать `apps`, замороженный в токене на момент последнего логина. Вызовы `/api/db` авторизуются по СТАРОМУ набору прав до перелогина или 10 лет.

**Реальный эффект:** владелец забирает доступ (например, после конфликта или смены роли) — а у сотрудника права фактически остаются старыми неограниченно долго. Не требует злоупотребления «потерянным» устройством — обычное легитимно работающее устройство сохраняет старые права молча.

**Направление фикса (не реализовано, ждёт решения):** `staffTokenRevoked()` уже делает один DB-запрос к `staff` по `id` на каждый вызов — тот же запрос можно использовать не только для `is_active`, но и чтобы взять живой `apps` из БД вместо доверия токену (без нового столбца, без доп. round-trip). Токен остаётся источником «кто», БД остаётся источником «что можно».

**Меняет отображаемые финансовые значения?** Нет — чистая авторизация.
**Меняет исторические данные?** Нет.
**Нужно решение владельца?** Да, до реализации — меняется модель доверия (токен перестаёт быть единственным источником прав), затрагивает все маршруты через `resolveCaller` (`/api/db`, `/api/notify`, `/api/bank/*`, `/api/storage/audit-photo`, `/api/google-reviews/sync-now`).

### AUTH-02 — «Сбросить устройство» не отзывает уже выданный токен

**Статус:** CONFIRMED. **Severity:** High.

**Evidence:**
- `app/dashboard/(shell)/team/page.tsx:158-161` — `resetDevice()` целиком делает одно: `staff.device_id = null`.
- `app/api/auth/pin/check/route.ts:113-116` — `device_id` проверяется ТОЛЬКО в момент логина (блокирует новый логин с несовпадающего устройства). К уже выданному токену это не имеет отношения.
- `lib/apiAuth.ts` — `resolveCaller`/`staffTokenRevoked` нигде не ссылаются на `device_id`.

**Текущее поведение:** владелец жмёт «Сбросить устройство» для сотрудника, залогиненного на устройстве A. Кука `mise_staff_token` на устройстве A не тронута, продолжает приниматься всеми API. Фактический эффект кнопки — «расковать устройство A, чтобы логин с устройства B больше не отклонялся по mismatch», а не «выгнать устройство A».

**Реальный эффект:** владелец, сбрасывающий устройство при потере/краже телефона сотрудника в уверенности, что это отключает доступ, — ошибается. Телефон продолжает работать.

**Направление фикса (не реализовано):** тот же механизм, что для AUTH-01, закрывает и это, если токен дополнительно понесёт `device_id` и сверяется с живым `staff.device_id`. Требует решения — это принципиально меняет UX кнопки (из «расковать» в «выгнать», что создаёт трение при легитимном перелогине).

**Меняет финансовые значения?** Нет. **Меняет исторические данные?** Нет.
**Нужно решение владельца?** ДА — какая семантика реально нужна: «расковать» (как сейчас) или «выгнать» (как подразумевает название кнопки).

### AUTH-03 — Нет защиты от дублирующихся активных PIN

**Статус:** CONFIRMED (на уровне кода/схемы). Наличие реальных дублей в проде — REQUIRES PRODUCTION VERIFICATION. **Severity:** High.

**Evidence:**
- `app/api/auth/pin/check/route.ts:99-119` — логин перебирает всех активных сотрудников ресторана (без `ORDER BY`, порядок не гарантирован) и делает `bcrypt.compare` построчно, возвращая **первое совпадение**.
- `app/api/auth/pin/hash/route.ts` — эндпоинт хэширования PIN не проверяет коллизии вообще.
- `app/dashboard/(shell)/team/page.tsx` — форма создания/правки PIN валидирует только формат (4 цифры), не сверяет с чужими PIN.
- Схема (`docs/migrations/*.sql`, схема-снапшот) — unique-констрейнта на `staff.pin_hash` нет (и не может быть — bcrypt-хэш соли разные для одного PIN, unique на хэше бессмысленен).

**Текущее поведение:** ничто не мешает двум активным сотрудникам одного ресторана иметь одинаковый 4-значный PIN. Если это произойдёт — логин аутентифицирует того, чья строка первой совпадёт в неупорядоченном запросе: неверная личность → неверные права (усиливает AUTH-01) → неверная посещаемость → неверная привязка устройства.

**Проверка дублей:** невозможна из репозитория напрямую (bcrypt-хэши нельзя сравнить между собой по значению). Нужен либо разовый серверный скрипт (сравнение через `bcrypt.compare` в цикле — N² по сотрудникам ресторана, дёшево при типичном размере команды), либо принять, что раньше момента внедрения проверки это не наблюдаемо.

**Направление фикса (не реализовано):** при сохранении PIN — серверная проверка кандидата против всех ДРУГИХ активных сотрудников того же ресторана через `bcrypt.compare` в цикле, отклонять с понятной ошибкой при коллизии. Только на новые/изменяемые PIN, не ретроактивно.

**Меняет финансовые значения?** Нет. **Меняет исторические данные?** Нет — только новая валидация будущих записей.
**Нужно решение владельца?** Направление — нет (однозначный технический гэп). Формулировка ошибки и нужен ли разовый прогон проверки существующих коллизий перед включением гейта — да, короткое подтверждение.

### FIN-02 — Погашение долга не атомарно

**Статус:** FIXED, ПОДТВЕРЖДЕНО. **Severity:** было High, сейчас закрыто.

`persistDebtSettlements` (`app/manager/page.tsx:349-368`) делает ОДИН вызов: `db.rpc('settle_debts', ...)`. Старый 3-шаговый путь полностью удалён, не оставлен рядом. ### ⚠ Флаг под правило заморозки — «История окладов» (uncommitted)

Не входит формально в список гипотез ТЗ, но напрямую попадает под FINANCIAL NUMBERS FREEZE — фиксирую отдельно.

`lib/salaryHistory.ts` + `docs/migrations/salary-history-2026-09.sql` подключены в КАЖДЫЙ путь чтения начисленной ЗП на обеих платформах (`manager/tabs-salary.tsx`, `people/tabs-salary.tsx`, `analytics/page.tsx`, `ManagerSalary.swift`, `PeopleModel.swift`, `AnalyticsView.swift`). Цель — реальный баг (правка `employees.salary` сегодня задним числом пересчитывала начисление за ВСЕ прошлые месяцы). Механизм: при первой правке оклада сотруднику вставляется sentinel-строка на `2000-01-01` со СТАРЫМ значением, дальше — по месяцам.

**Это правильный фикс реального бага. Но по определению правила заморозки:**
- Не трогает: `shift_expenses`, `salary_payments`, `inkassations` — ни одна сохранённая денежная запись не переписывается.
- Трогает: то, что ОТОБРАЖАЕТСЯ/ВЫЧИСЛЯЕТСЯ на экранах Payroll/Analytics за прошлые месяцы для любого сотрудника, у кого будет правка оклада ПОСЛЕ выката фичи — начисление за прошлые месяцы переключится с «текущий оклад» на «зафиксированный старый оклад» (то, что и должно было быть, но не было раньше).
- Сотрудники без единой правки оклада после выката — поведение не меняется (фолбэк на текущее значение).

**Требуется твоё решение до коммита этого диффа**, конкретно: пример BEFORE/AFTER на одном реальном сотруднике с историей правок, чтобы ты видел ровно что изменится на экране, прежде чем это уйдёт в прод.

### AN-01 — Определение «Выручка» по экранам

**Статус:** CONFIRMED — реальное расхождение найдено, HIGH SENSITIVITY, фикс НЕ предлагается.

Основная формула (Analytics, обе платформы) **идентична и корректно завязана на тумблер**:

```
web:  adjustCard(rows) = includeCard ? rows.map(income += income_card) : rows   [app/analytics/page.tsx:658-660]
iOS:  adj(rows)        = includeCard ? rows.map(income += income_card) : rows   [AnalyticsView.swift:387-389]
```

Web и iOS экраны Analytics и «Доход»-карточка ведут себя одинаково: при `include_card_in_analytics=false` — доход = только нал; при `true` — нал+карта.

**Найденное расхождение — в AI-контексте:**

| Поверхность | Формула | file:line | cash=600/card=400, includeCard=**false** |
|---|---|---|---|
| Web Analytics UI «Доход» | includeCard-зависимая | `app/analytics/page.tsx:658-660,671` | 600 |
| Web AI-советник, поле «доход» | та же includeCard-зависимая `totalIncome` | `app/analytics/page.tsx:743` | 600 |
| iOS Analytics UI «Доход» | includeCard-зависимая | `AnalyticsView.swift:387-394` | 600 |
| **iOS AI-советник, поле «Revenue»** | **БЕЗУСЛОВНО нал+карта, игнорирует тумблер** | `AnalyticsView.swift:136-138` | **1000** |

Код на iOS содержит явный комментарий, объясняющий это как намеренное решение: *«ИИ должен видеть полную выручку (нал+карта) независимо от переключателя includeCard, который влияет только на то, что владелец решил показывать в UI»*. То есть это осознанный выбор для iOS — но web AI-советник этому же принципу не следует, у него «доход» = то же самое, что показано на экране (может быть заниженным при `includeCard=false`).

**Вопрос владельцу:** должен ли AI-советник на ОБЕИХ платформах всегда видеть полную выручку (текущее намерение iOS), или обе платформы должны единообразно уважать тумблер (текущее поведение веба)? Разные владельцы разумно могут хотеть разного — не меняю без ответа.

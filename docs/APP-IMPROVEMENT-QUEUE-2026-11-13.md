# Очередь доработок приложения

Пользователь попросил разбирать проблемы по одной, уточнять поведение до реализации
и проверять изменения, включая iOS-симулятор. Публикацию и перенос региона отложить
до завершения согласованного набора задач. Предыдущие изменения сохранить.
Уточнение пользователя после Booking: оставшиеся полные аудиты провести в конце,
после конкретных доработок. Проверки каждого исправления выполнять сразу.

## 1. Произвольные расходы смены — реализовано локально

Существующие расходы из настроек остаются готовым шаблонным списком: расход может
отсутствовать в конкретной смене. Добавить «+», название и сумму нового расхода.
Сохранённые названия предлагать при вводе в следующих сменах: например, «P» →
«Парфюм», если такое название уже использовали. Пользователь подтвердил: названия остаются только в истории подсказок,
не добавляются в постоянные шаблоны. iOS, Manager web и dashboard реализованы;
проверки описаны в docs/superpowers/plans/2026-11-13-custom-expenses.md. Выпуск отложен. Учесть восстановление/редактирование смены,
черновики, расчёт итогов, долги, отчёты, повторное сохранение и изоляцию заведений.

Наблюдение по текущему коду: native ManagerView и web app/manager строят поля
из expense_categories; сохранение и splitShiftExpenses зависят от ID категорий.
Нельзя просто добавить поле в интерфейс без проверки полного пути сохранения.

## 2. Booking — аудит и локальные исправления

Проверены Booking, Guests и Google Reviews. Пользователь разрешил параллельные
исправления с последующей перепроверкой. Реализованы серверные права/валидация,
сохранение без дублей, защита от запоздавших ответов, сохранность черновиков,
стабильная связь гостя с заметками, атомарные операции гостя, полная история,
корректные визиты и последние отзывы. Независимая проверка нашла дополнительные
ошибки телефона, статуса при навигации и повторов уведомлений; они также исправлены.
SQL-миграция подготовлена и проверяется только на временной локальной PostgreSQL.
В рабочую базу не применялась, выпуск отложен. Подробности и ограничения —
docs/BOOKING-FIXES-VERIFICATION-2026-11-13.md.

## 3. Stash: клавиатура и несколько позиций — реализовано локально

В приходе, выдаче и списании активное поле прокручивается над клавиатурой. Общая
цепочка фокуса и «Далее/Готово» работают для ручных строк, выбора со склада и причины
списания; новая строка/бренд получает фокус. В ходе проверки исправлен вылет при
удалении активной строки/карточки. Проверены шесть ручных позиций, складские позиции,
оба вида списания, светлая/тёмная темы в iPhone-симуляторе на офлайн-фикстурах.
Сборка и регрессионные тесты прошли. Подробности:
docs/superpowers/plans/2026-11-13-stash-keyboard.md. Выпуск отложен.

## 4. Закрытие смены: долгое сохранение — реализовано локально

Убрано ожидание необязательной сводки/push после финансовых записей. Расходы
категорий и сотрудников сохраняются одним пакетом; повторное чтение расходов
убрано только для сценария без изменений разовых расходов и погашения долгов.
Дата и ввод защищены во время записи, ошибки оставляют форму доступной для повтора.
Проверены успешное закрытие, ошибка и повтор в iOS-симуляторе на офлайн-данных;
финансовые регрессии, сборка и независимая проверка кода. Контрольный замер с
80 мс/запрос: около 425 → 259 мс, без ожидания необязательной сводки/уведомления.
Это не замер рабочей сети. Подробности:
docs/superpowers/plans/2026-11-13-shift-save-performance.md. Выпуск отложен.

## 5. Stash: долгое сохранение движений — реализовано локально

Приход, выдача и списание сохраняют движения/новые товары пакетами. Атомарные
серверные обновления остатков возвращают подтверждённые записи сразу; полная
перезагрузка склада, инвентаризаций и продаж после успеха не нужна. Остаток зала
пересчитывается по сохранённым движениям с учётом исторической недостачи и смены
источника при редактировании. Ввод смены не сбрасывается. Начальная загрузка,
ошибки/повторы и устаревшие ответы покрыты регрессиями. Проверены три операции по
шести позициям и списание с зала в симуляторе на офлайн-данных. Контрольный замер
выдачи: 21 → 8 запросов, около 428 → 251–264 мс при 80 мс/запрос; это не рабочая сеть.
Подробности: docs/superpowers/plans/2026-11-13-stash-save-performance.md. Выпуск отложен.

## 6. Авансы: долгое сохранение — реализовано локально

Нативный Manager не пересчитывает зарплаты всех сотрудников за два месяца после
успешного аванса. Независимые проверки выполняются параллельно, баланс инкассации
читается свежим. Обязательные денежные записи, CAS и откат сохранены. Подтверждённый
аванс сразу обновляет историю, наличную часть и остаток; месяц защищён от смены при
записи, копейки нормализованы. Форма ждёт результат и сохраняет сумму/дату при ошибке.
Контрольный замер: 18 → 5 запросов, около 606 → 252–259 мс при 80 мс/запрос (не рабочая сеть).
В симуляторе проверены успешная выдача, отказ списания/откат и успешный повтор без
дублей. Подробности: docs/superpowers/plans/2026-11-13-advance-save-performance.md.
Сборки/регрессии/локальный сканер прошли. Выпуск отложен, рабочая база не изменялась.

## 7. Главный экран: размеры и перестановка плиток — реализовано локально

Плитки сохраняют идентичность между строками; перенос использует неизменный снимок
геометрии и записывает результат после отпускания. Короткое движение внутри своей строки
не отправляет плитку в конец. Размеры S/M/L меняются без растягивания поверх соседей;
добавлен точный выбор размера по нажатию на ручку. Отмена очищает состояние жеста,
сохранённые повторяющиеся модули отфильтровываются с сохранением существующего порядка.
Проверены перенос, размеры, длинная сетка из шести L, прокрутка в режиме правки,
обычное открытие модулей и сохранение после перезапуска в iOS-симуляторе на офлайн-данных.
Регрессии покрывают 2 187 комбинаций размеров/ширины и хранение отдельно для сотрудников.
Подробности: docs/superpowers/plans/2026-11-13-hub-tiles.md. Выпуск отложен.

## Находки для отдельного последующего разбора

- В локальной версии SQL settle_debts при погашении долга той же сменой оригинал
  и новая строка могут получить одинаковый paid_shift_id и затем учитываться дважды.
  Поведение рабочей БД отдельно не проверялось. В новом интерфейсе разовых расходов
  долг текущей смены оплачивается переключателем строки, а не этим сценарием RPC.
  Общий путь погашения долгов оставить для отдельного разбора; в рамках пункта1 его
  финансовый алгоритм не переписывался.

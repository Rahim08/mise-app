## ВАЖНО

### 1. `persistInkassation` — delete-перед-insert на денежных данных (iOS)
`native/Mise/Mise/ManagerView.swift:285-294`. Старый близнец в `persistExpenses` починен (insert-перед-delete, `:253-282`), инкассация — нет: `delete().eq("shift_id")` затем `insert`. Плюс `persist()` гоняет `shiftUpdate` и `persistInkassation` параллельно (`async let`, `:304-309`).
- **Проблема:** обрыв сети между delete и insert → строка инкассации стёрта, не пересоздана; `closing_balance` мог уже записаться. Analytics читает `inkassations.total` → неверный нетто.
- **Повтор:** менеджер, кассовая смена, «Закрыть» при плохой сети (подвал/метро). Delete прошёл, insert упал. `save()` покажет ошибку; если не повторить (закрыл приложение) — инкассация смены потеряна в БД.
- **Решение:** insert новой строки → delete старой по собранному id (как уже сделано для расходов); либо серверный upsert по `shift_id`.

### 2. Заказ со столом исчезает из инбокса iOS (рассинхрон типов)
`menu_orders.table_number` — тип **`text`** (миграция menu-platform), веб шлёт строку из `?table=` (`app/menu/[slug]/page.tsx:171,325`), но Swift декодит `MenuOrder.table_number: Int?` (`Models.swift:175`).
- **Проблема:** Postgres возвращает text-колонку JSON-строкой («5»). `Int?` не коэрсит строку → бросок → `Lossy`-обёртка (`DB.swift:96-101,189`) обнуляет **всю строку заказа** → заказ пропадает из списка на iOS (`PeopleView.swift:945-951`). Даже число «5» ломает (хранится как текст).
- **Повтор:** гость сканирует QR со ссылки с `?table=5`, делает заказ. На вебе виден, на iPhone официанта/менеджера — нет.
- **Решение:** сделать Swift `table_number: String?` (и рендер соответственно) — веб и БД уже строковые.

### 3. Деплой кода меню без миграции ломает сохранение меню
Незакоммиченная миграция `menu qr-features migration.sql` (в **корне репо**, не в `docs/migrations/`) добавляет `menu_items.intensity/stock_left`, `menus/menu_settings.quick_actions/design/card_style`. Незакоммиченный код dashboard уже их **пишет**: `app/dashboard/(shell)/menu/page.tsx:533-534` (item), `:108` + сохранение settings.
- **Проблема:** публичное чтение — `select('*')` (терпит отсутствие колонок, `app/api/menu/[slug]/route.ts:17`), но запись из билдера с несуществующей колонкой → Supabase 400 → владелец не может сохранить ни позицию, ни оформление меню.
- **Повтор:** задеплоить код раньше SQL → любое сохранение в билдере меню падает.
- **Решение:** применить SQL на проде ДО деплоя (заголовок файла это и требует). Перенести файл в `docs/migrations/`, убрать пробелы из имени.

### 4. Cron шлёт хардкод-русские пуши всем ресторанам (i18n)
`app/api/cron/reminders/route.ts`: `shift_reminder` (`:335-336`), `purchase`-дайджест (`:169-170`), `trial_ending` (`:52`) пишут `title`/`body` строкой напрямую, минуя `notifyStrings.ts`. Локализованы только `runScheduledAudits`/`remindOpenCloseChecklist` (через `dispatchNotification` с ключами).
- **Факт по ключам:** в `notifyStrings.ts` НЕТ ключей для shift_reminder и trial_ending (надо добавить); ключи `notify.purchaseTitle/purchasePositionsBody` есть, но дайджест их игнорирует.
- **Проблема:** итальянский/французский/турецкий ресторан получает пуш на русском. Прямо против правила «пуши на языке получателя».
- **Повтор:** любой не-русский ресторан с графиком на завтра → 18:00 UTC приходит «Ваша смена завтра».
- **Решение:** перевести три пути на `dispatchNotification` с ключами; добавить недостающие ключи в `notifyStrings.ts`.

### 5. Роль `admin` — живая в UI, мёртвая в логике
Выбирается в форме команды (`components/dash/shared.tsx:27`, `ROLE_OPTS` содержит `admin`). Привилегий не даёт нигде: `isManager = !!me.is_owner || me.role === 'manager'` (`app/people/page.tsx:2461`); iOS то же (`AppModel.swift:42,48`, `MainView.swift:319`); `canSeeMoney = role === 'owner' || role === 'manager'` (`app/tobacco/page.tsx:386`). `role === 'admin'` не встречается нигде.
- **Проблема:** владелец назначает «Администратор», ждёт прав менеджера — сотрудник получает рядового. Fail-closed (не дыра), но вводит в заблуждение.
- **Решение (нужно ваше):** либо добавить `admin` в `isManager`/`canSeeMoney` на обеих платформах, либо убрать из `ROLE_OPTS`.

### 6. Доступ «Mise Menu» для сотрудника не работает через шлюз
Форма команды предлагает `menu` как выдаваемый доступ (`components/dash/shared.tsx:8-14`). Шлюз знает только 4 AppId (`app/api/db/route.ts:16`), menu-таблицы привязаны к `people` (`:41-46`). Сотрудник с `apps=['menu']` не проходит `authorized()` (`:109`) ни на одной таблице.
- **Проблема:** выдаёшь только «Mise Menu» (напр. для стоп-листа) — сотрудник логинится и не может ничего. Стоп-лист `menu_items` требует `people`, а UI предлагает `menu`. Плюс путь `menu` = `/dashboard/menu` (owner-роут), а не PIN-приложение.
- **Решение (нужно ваше):** либо `menu` даёт доступ к menu-таблицам (добавить AppId + правки POLICY), либо убрать `menu` из выдаваемых сотрудникам.

### 7. Авто-прогул считает время без таймзоны ресторана
`app/api/cron/reminders/route.ts:110-113`: `shift_start` («HH:MM») кладётся в `new Date(now)` через `setHours` в UTC (Vercel). `fmtDate` тоже UTC (`lib/format.ts:5-7`). Таймзона ресторана не учитывается нигде.
- **Проблема:** для UTC+2/+3 «grace истёк» срабатывает со сдвигом на часы → черновик прогула не вовремя (или неверный день у смен близко к полуночи). Прогул = `deduct_per_absence` из ЗП → денежные последствия.
- **Повтор:** ресторан не в UTC, сотрудник с опубликованным графиком → авто-прогул на неверном рубеже.
- **Решение (нужно ваше):** хранить/применять таймзону ресторана в cron-расчётах дня и grace.

## ВАЖНО (новое)

### 12. Кеш SELECT в iOS делает pull-to-refresh пустышкой и задерживает межустройственную синхронизацию до 5 минут
`DB.swift:131` — свежий кеш (моложе TTL=5 мин) возвращается **вместо похода в сеть всегда**; способа принудительно обойти кеш нет. `refreshable` (`MainView.swift:204`, `ManagerView.swift:486`) зовёт те же load-функции с тем же payload → тот же ключ кеша → сеть не трогается.
- **Проблема:** мутации инвалидируют кеш только на том же устройстве. Всё, что изменил веб/другой iPhone (новый заказ, стоп-лист, бронь, закрытая смена), не появится на устройстве до 5 минут — и жест «потянуть-обновить» это не лечит, хотя пользователь уверен в обратном.
- **Повтор:** открыть «Заказы» в People на iPhone → гость делает заказ через QR → тянуть-обновить на iPhone → заказа нет (до 5 мин).
- **Решение:** параметр `force`/`bypassCache` для refresh-путей (refreshable всегда мимо кеша), либо короткий TTL для «горячих» таблиц (menu_orders, bookings), либо инвалидация кеша в `.refreshable` перед load.

### 13. Зарплата считается по-разному на вебе и в iOS (деньги)
Один сотрудник видит разные суммы «наличными» на двух платформах:
- **Авансы:** iOS вычитает `salary_advances` (`PeopleView.swift:294-310`), веб-People их **вообще не читает** (`app/people/page.tsx:749-772`, grep по репо — ноль обращений к salary_advances на вебе).
- **Карта:** веб фолбэчит на `employees.card_amount`, если нет помесячной записи (`page.tsx:767`); iOS осознанно НЕ фолбэчит (комментарий «иначе прилипало», `PeopleView.swift:303-305`). Правила противоречат друг другу.
- **Авто-прогулы:** iOS исключает `source == "auto"` из удержаний (`PeopleView.swift:297`), веб удерживает за все прогулы включая авто-черновики (`page.tsx:751` — source не выбирается и не фильтруется).
- **Повтор:** сотрудник с авансом и авто-прогулом открывает «Зарплата» в iOS и на вебе — три расхождения сразу.
- **Решение (нужно ваше):** какая модель каноническая? Привести вторую платформу к ней.

### 14. `lte("date", ym + "-31")` — невалидная дата в 30-дневных месяцах (авансы)
`PeopleView.swift:295` и `AnalyticsView.swift:464` строят верхнюю границу как `"2026-06-31"`. Если `salary_advances.date` имеет тип `date` (таблицы нет ни в CSV-интроспекции, ни в migrations/ — тип не подтверждён), Postgres отвергнет фильтр → 400 → `try?` молча даст пустой список → авансы «исчезают» из расчёта в июне/апреле/сентябре/ноябре (и феврале).
- **Решение:** считать последний день месяца как в `AnalyticsView.swift:194` (`key(monthEnd)`) — безопасно при любом типе колонки. Тип колонки проверить в Supabase (открытый вопрос).

### 15. Менеджер не может сохранить «порог опоздания» — write-гейт owner-only
POLICY `restaurant_settings: write []` (`app/api/db/route.ts:22`), но редактор порога в «Дисциплине» пишет её с PIN-сессии: iOS `PeopleView.swift:1083` (покажет ошибку и откатит), веб `app/people/page.tsx:2263-2266` — **результат запроса не проверяется вовсе**: менеджер двигает слайдер, видит «сохранилось», после перезагрузки значение возвращается.
- **Решение (нужно ваше):** разрешить write `late_grace_min` менеджеру (отдельный узкий путь) или спрятать редактор за owner.

### 16. Чек-листы: lost-update при параллельных отметках + дыры оффлайн-очереди
a) `toggleChecklistItem`/`toggleAuditItem` пишут **весь массив** `items_state`, собранный из локального состояния (`PeopleView.swift:743-782, 643-680`; веб аналогично). Два человека отмечают разные пункты одного листа почти одновременно → last-write-wins, первая отметка стирается.
- **Повтор:** официант и бармен отмечают пункты общего чек-листа открытия с двух телефонов в одну минуту.
b) Оффлайн-очередь покрывает только UPDATE-путь: первая отметка нового прогона (INSERT, `:772-778`) без сети просто падает с flash — не queue'ится, в отличие от `:767-769`.
c) `flushPendingChecklistQueue` (`:804-829`) перечитывает состояние SELECT'ом, который может прийти из кеша 5-минутной давности (см. 12) → перезапись чужих свежих отметок усугубляется.
- **Решение:** перейти на дельта-апдейты (jsonb_set по индексу пункта через RPC) либо перечитывать с обходом кеша и мержить по индексам, а не перезаписывать массив.

### 17. У iOS нет чек-аута — «отработанные часы» для iOS-сотрудников всегда 0
Веб-People имеет кнопку ухода с гео (`app/people/page.tsx:594`, пишет `check_out_at/lat/lng`); в iOS `check_out` нигде не пишется (grep: только отображение `PeopleView.swift:1928,1965`). Веб-зарплата показывает «Отработано» из `hoursOf()` (`page.tsx:499-500`) — для тех, кто отмечается с iPhone, всегда 0 ч.
- **Решение:** добавить чек-аут в iOS (паритет), либо убрать «Отработано» из расчёта, пока паритета нет.

### 18. Новые быстрые вызовы «уголь/вода» не поняты iOS-инбоксом
Незакоммиченный код веба шлёт `coal_call`/`water_call` (маркер `items[0].call = "coal"|"water"`, `app/api/menu/order/route.ts:17-19`). iOS определяет вызов как `call == "waiter"` (`PeopleView.swift:3663`) → «уголь»/«вода» отрисуются как обычный заказ с 0 позиций на 0. Поверх находки 2 (`table_number` text валит всю строку) — вызов со стола вообще не дойдёт.
- **Решение:** iOS: `isCall = call != nil`, подписи/иконки по виду вызова; и починить находку 2 до деплоя веб-кода.

### 19. Генерация PDF бизнес-отчёта блокирует main thread
`ReportModel` объявлен `@MainActor` (`ReportExportView.swift:9`), `generate()` зовёт `buildPDF` внутри Task, наследующего MainActor (`:615-624`) — многостраничный рендер `UIGraphicsPDFRenderer` идёт на главном потоке.
- **Повтор:** Настройки → Бизнес-отчёт → период «всё время» при годовой истории смен → интерфейс замирает на всё время генерации (спиннер не крутится).
- **Решение:** вынести рендер в `nonisolated`/`Task.detached`, передав уже подготовленные данные.

### 20. `/api/db` update не вычищает `restaurant_id` из values
`route.ts:167`: insert/upsert прогоняются через `forceScope`, а `update(values)` — нет. Сотрудник с write-доступом к любой таблице может послать `update({restaurant_id: <чужой rid>})` и «перекинуть» свои строки в чужой ресторан (вандализм своих данных + мусор в чужом списке — например, чужие bookings/news_posts, где write у всех модулей).
- **Решение:** в update удалять `scope`-колонку из values (или явно запрещать её менять).

### 21. iOS хаб: сабтайтлы модулей — хардкод-русские
`MainView.swift:13-18`: «Смены и касса», «Выручка и аналитика», «Склад и кальян», «Команда и расписание», «Брони столов», «Лента и объявления» — мимо `Localization.swift`. Итальянец/турок видит русский текст на главном экране. Прямое нарушение правила «все экраны локализованы».

### 22. Stash-only сотрудник: тихая деградация двух фич из-за POLICY
`restaurant_settings.read = ['manager','analytics','people']` — без `stash` (`route.ts:22`):
- `StashView.swift:74` (free_hookah_categories) → 403 → кальянщик получает дефолтные категории бесплатных кальянов вместо настроенных;
- `GoogleReviewsView.swift:21` (google_place_id) → 403 → вкладка «Отзывы» (доступна всем через Bookings) у stash-only сотрудника вечно в состоянии «не подключено».
- **Решение:** добавить `stash` в read restaurant_settings (или отдельный узкий select-путь).

### 23. `stock_left` («Осталось N») не уменьшается заказами
Миграция qr-features вводит счётчик, билдер его выставляет (`dashboard/menu/page.tsx:534`), гостевое меню показывает и блокирует при 0 (`app/menu/[slug]/page.tsx:407`), но `/api/menu/order` его **не декрементит**. Счётчик чисто ручной: гости могут заказать больше стока, «Осталось 3» висит до ручной правки.
- **Решение (нужно ваше):** авто-декремент в order-роуте (с floor 0) — или это осознанно «ручной лимит дня»?

## ЖЕЛАТЕЛЬНО (новое)

### 24. Веб-дизайн: мобильная навигация из 12 скроллящихся пилюль
`(shell)/layout.tsx:247-267` — 12 пунктов в горизонтальной прокрутке без индикации продолжения. По NN/g «out of sight is out of mind»: пункты за краем (Team, Settings, Billing — они в конце) теряются; скроллируемым барам нужен «подглядывающий» следующий пункт. Рекомендация: нижний таб-бар на 4-5 главных + «Ещё» (или группировка), либо хотя бы peek следующей пилюли и порядок по частоте. Источники: [NN/g Mobile Navigation Patterns](https://www.nngroup.com/articles/mobile-navigation-patterns/), [Setproduct Tab UI rules](https://www.setproduct.com/blog/tabs-ui-design), [Eleken SaaS dashboard patterns](https://www.eleken.co/blog-posts/saas-dashboard-design).

### 29. Хардкод-русский в веб-зарплате
`app/people/page.tsx:502-504` — `fmtHours` возвращает «ч»/«м» строками; `:742` — monthLabel всегда 'ru-RU'. Страница в остальном локализована.

### 30. `checkStaffPlanLimit` считает обновляемые места только по eq-id
`route.ts:102` — update по другому фильтру (не `id eq`) даст двойной счёт текущего сотрудника и ложный «лимит тарифа». Сейчас UI шлёт только по id — латентно.

### 31. Корень бага Sprint 1: градиент «e» не зациклен
`Brand.swift:12-27` — палитра `g + g.reversed()` растянута на 3 ширины, окно уезжает с `[0..w]` до `[2w..3w]` и прыгает назад. Начальный и конечный сегменты — зеркальные отражения (blue→pink против pink→blue), а не совпадающие → в момент рестарта цикла направление переливания視 «ломается». Для бесшовности нужен повтор палитры (`g + g + [g0]`) со сдвигом ровно на один период, а не зеркало.

### 32. Кандидат корня «бегущих слов после logout»: повторный `onAppear` наслаивает repeatForever
`Brand.swift:30-35` — каждый `onAppear` делает `phase = 0` и вешает новый `.repeatForever`. После logout (`phase = .welcome`) WelcomeView с Wordmark появляется заново; если SwiftUI сохраняет идентичность вью (ZStack-switch в `OnboardingView.swift:9-15` + анимация фазы), к той же @State-переменной прикладывается вторая бесконечная анимация поверх недоснятой первой → хаотичное дёргание градиента/текста. Лечится TimelineView-ом вместо state-анимации либо `.id()` пересозданием при смене phase. (Точный симптом на устройстве не воспроизводился — механизм подтверждён кодом.)

### 33. Тумблеры уведомлений iOS не влияют на локальные пуши: `mise_notif_prefs` никто не пишет
Экран настроек уведомлений пишет только в БД `notification_prefs` (`MainView.swift:383-402`) — ключ UserDefaults `mise_notif_prefs` в проекте **никогда не записывается**, но читается двумя местами: `Push.swift:146-149` (`ShiftReminder.isEnabled` — локальное напоминание «закройте смену») и `StashView.swift:409-411` (гейт отправки low_stock).
- **Проблема:** выключенный тумблер «Напоминание о смене» не выключает локальное уведомление — оно планируется всегда (`prefs == nil → true`). Гейт low_stock у отправителя всегда открыт (сервер, впрочем, дофильтрует по prefs получателя — тут лишь мёртвая логика).
- **Решение:** `ShiftReminder.isEnabled` должен читать серверные prefs (или зеркалить их в UserDefaults при сохранении в MainView).

### 34. Face ID: системный диалог всегда по-русски
`AppModel.swift:104` («Вход в Mise») и `OnboardingView.swift:302` («Включить вход по Face ID») — hardcoded-русские reason-строки системного промпта Face ID. Итальянец видит русский текст в системном диалоге. В копилку находки 21.
